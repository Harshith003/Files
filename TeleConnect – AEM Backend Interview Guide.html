Project Structure Overview

TeleConnect is a standard AEM Maven multi-module project (also called an archetype project). Here's what each folder does:

📁 core/

All Java backend code — Models, Schedulers, Filters, Listeners, Servlets. This is the OSGi bundle.

📁 ui.apps/

JCR content that goes under /apps — component HTL templates, clientlibs (CSS/JS), component definitions (.content.xml).

📁 ui.content/

JCR content under /content — actual pages, templates, configurations. (Not shown but standard AEM structure.)

📁 all/

The packaging module. Combines all submodules into one deployable ZIP (content package) for AEM.

📄 pom.xml (root)

Parent POM. Declares all submodules, dependency versions (AEM API, Sling, Jackrabbit, etc.).

📁 it.tests/

Integration tests. CreatePageIT and GetPageIT test page creation/retrieval against a running AEM instance.

Models — Sling Models (7 Files)

☕ HeaderModel.java Sling Model
@Model(adaptables = SlingHttpServletRequest.class, defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL)
@Model registers this class as a Sling Model. adaptables = SlingHttpServletRequest.class means this model is created by adapting an incoming HTTP request — so it can access request, resource, and session context. DefaultInjectionStrategy.OPTIONAL means if a property is missing in JCR, it won't throw an error — it simply injects null instead of failing.
@ValueMapValue private String logoPath;
@ValueMapValue reads the property named logoPath directly from the component's JCR node (the ValueMap). This is what an author stores in the component dialog. The field name must match the JCR property name (or you can use name = "..." to override).
@ChildResource private List<NavLink> navLinks;
@ChildResource reads a child node of the component node named navLinks and maps each sub-node to the inner NavLink class (which is itself a Sling Model adaptable from Resource). This is how multi-field dialogs (navigation links added by the author) are mapped to Java objects.
static class NavLink — @ValueMapValue linkText, linkIcon, linkPath
The inner static class is also annotated @Model(adaptables = Resource.class). Each child resource under navLinks gets adapted into one NavLink. This pattern — an outer model with a List of inner models — represents a nested/multifield JCR structure.
☕ FooterModel.java Sling Model
@Model(adaptables = SlingHttpServletRequest.class, ...)
Same pattern as HeaderModel. Adaptable from request so it can read session context if needed.
@ValueMapValue private String copyrightText;
Reads the copyrightText property from the footer component's JCR node — set by the author in the dialog.
@ChildResource private List<FooterLink> footerLinks;
Maps multi-field footer links (stored as child nodes) into a list of FooterLink objects. Inner class has linkText and linkPath. Same nested Sling Model pattern as HeaderModel.
☕ HeroBannerModel.java Sling Model
@Model(adaptables = Resource.class, defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL)
This model is adaptable from Resource (not the full request). It is a simpler, lighter model — only needs the resource (component node) to read its properties. No session-level access needed.
@ValueMapValue — pretitle, title, description, primaryLinkText, primaryLinkUrl, secondaryLinkText, secondaryLinkUrl
All content fields for the hero banner section. Each annotation reads the matching JCR property from the component dialog. These are author-editable fields that appear on the homepage hero section.
@ValueMapValue — stat1Value, stat1Label, stat2Value, stat2Label, stat3Value, stat3Label
Six fields for the 3 statistics displayed in the hero (e.g., "500M+ Customers"). Each stat has a value and label, stored separately in JCR.
☕ ProductHighlightModel.java Sling Model
@Model(adaptables = SlingHttpServletRequest.class, ...)
Request-adaptable model for the product highlight banner shown on Prepaid/Postpaid/Broadband pages.
@ValueMapValue — productTitle, description, bannerImage
Three simple authored properties. bannerImage typically stores a DAM path like /content/dam/teleconnect/images/hero.jpg. The HTL template conditionally renders the image only if bannerImage is non-null.
☕ PlanListModel.java Sling Model + Content Fragments
@Model(adaptables = SlingHttpServletRequest.class, ...)
Request-adaptable because it needs ResourceResolver to traverse the JCR tree and find Content Fragments in DAM.
@SlingObject private ResourceResolver resourceResolver;
@SlingObject injects the current request's ResourceResolver. This is used to navigate to DAM paths and read Content Fragment resources. This is the Sling Resource API in action.
@ValueMapValue private String sectionTitle; @ValueMapValue private String productType;
productType (prepaid / postpaid / broadband) is authored in the component dialog. Based on this value, the model resolves the correct CF folder path in DAM.
@PostConstruct protected void init()
@PostConstruct is called automatically after all injections are done. It is the initialization method — logic here:
1. Call getCfRootPath(productType) to map productType → DAM folder path.
2. Use resourceResolver.getResource(cfRootPath) to get the DAM folder.
3. Iterate all children, adapt each to ContentFragment.
4. Read each CF element (planName, cost, validity, benefits, etc.) and build PlanItem list.
ContentFragment cf = child.adaptTo(ContentFragment.class);
This is the Content Fragment API. adaptTo(ContentFragment.class) converts a Sling Resource (the CF node in DAM) into a ContentFragment object so you can call getElement(elementName) to read each field. This is a core AEM Content Fragment concept.
private String getCfRootPath(String type) — switch on prepaid/postpaid/broadband
Maps the authored productType to the corresponding DAM folder:
• prepaid → /content/dam/teleconnect/telconnectplans/prepaidplans
• postpaid → /content/dam/teleconnect/telconnectplans/postpaidplans
• broadband → /content/dam/teleconnect/telconnectplans/broadbandplans
private String getElementValue(ContentFragment cf, String elementName)
Null-safe helper method. Calls cf.getElement(elementName).getValue().getValue() wrapped in try-catch so that missing fields return empty string instead of crashing.
public List<PlanItem> getPlans() / public boolean getHasPlans()
Getter methods exposed to the HTL template. In HTL, ${model.plans} calls getPlans() and ${model.hasPlans} calls getHasPlans(). Java Bean naming convention is critical here.
static class PlanItem — planName, cost, validity, benefits, addedAdvantage, offers, productType
A plain Java POJO (no Sling Model annotation needed here) that holds one plan's data. The list of these is returned to the template. Not an inner Sling Model because data comes from CF elements, not from resource adaptation.
☕ SchedulerPlanListModel.java Sling Model (Scheduler Data)
@ValueMapValue private String plansRootPath; @ValueMapValue private Long initialCount;
Unlike PlanListModel (which reads from DAM Content Fragments), this model reads plan data from CQ Pages created by the PlanCardScheduler. The plansRootPath is authored in the component dialog pointing to the parent page containing all imported plan pages.
instanceId = Integer.toHexString(request.getResource().getPath().hashCode());
Generates a unique ID based on the component's JCR path. This is used in HTL as a unique HTML element ID (id="splGrid_${model.instanceId}"). This is important when the same component is used multiple times on a page — avoids HTML ID collisions.
for (Resource child : pageResource.getChildren()) — check jcr:primaryType == cq:Page
Traverses child pages of the configured root path. Checks jcr:primaryType = cq:Page to skip any non-page resources. Then gets jcr:content of each page and reads plan properties from the ValueMap (these were written by PlanCardScheduler).
public int getInitialCount() — returns initialCount or default 4
Controls how many plan cards are shown initially (before "See More" is clicked). The value is authored in the dialog; defaults to 4 if not set. The JavaScript in schedulerplanlist.js uses this data-initial attribute to hide/show extra cards.
☕ HelloWorldModel.java Sling Model (Demo)
@Model(adaptables = Resource.class)
Resource-adaptable demo model. This is from the AEM archetype and demonstrates basic Sling Model concepts.
@ValueMapValue(name=PROPERTY_RESOURCE_TYPE, injectionStrategy=InjectionStrategy.OPTIONAL) @Default(values="No resourceType")
@Default provides a fallback value if the property is missing. injectionStrategy=InjectionStrategy.OPTIONAL at field level overrides the class-level strategy for this specific field.
@SlingObject private Resource currentResource; @SlingObject private ResourceResolver resourceResolver;
@SlingObject injects Sling API objects directly — the current resource and resolver.
@PostConstruct init() — PageManager → getContainingPage → page path
Uses resourceResolver.adaptTo(PageManager.class) to get the WCM PageManager, then finds which CQ Page contains the current component resource. Demonstrates the adaptTo pattern for accessing AEM services from models.

Schedulers

⏰ PlanCardScheduler.java OSGi Scheduler
@Component(service = Runnable.class, immediate = true)
Registers this as an OSGi Component. service = Runnable.class tells OSGi this is a Runnable — which is how Sling Scheduler picks it up. immediate = true means activate it right when the bundle starts, without waiting for any service request.
@Designate(ocd = PlanCardScheduler.Config.class)
@Designate connects this component to its OSGi configuration (the inner Config interface). The configuration appears in AEM's OSGi Console (/system/console/configMgr) where an admin can change the cron expression and CSV paths without redeploying code.
@ObjectClassDefinition — Config interface with @AttributeDefinition fields
The inner Config interface defines configurable properties:
• schedulerName — name used to register/unregister the job
• cronExpression — "0 * * * * ?" means run every minute
• prepaidCsvPath, postpaidCsvPath, broadbandCsvPath — DAM paths to CSV files
@Reference private ResourceResolverFactory resourceResolverFactory; @Reference private Scheduler scheduler;
@Reference is the OSGi dependency injection for services. ResourceResolverFactory creates ResourceResolvers for reading JCR. Scheduler is the Sling Scheduler service to register the cron job.
@Activate activate(Config config)
Called when the component is activated (bundle starts or config changes). Saves the config and calls addScheduler() to register the cron job using scheduler.EXPR(config.cronExpression()).
@Deactivate deactivate()
Called when the bundle is stopped. Calls removeScheduler() which calls scheduler.unschedule(name) — important to clean up, otherwise old scheduled jobs pile up.
public void run() — getAdministrativeResourceResolver → importPlans × 3
This is what runs on every cron tick. It:
1. Opens an administrative ResourceResolver (service user, wide access)
2. Calls importPlans() for prepaid, postpaid, and broadband CSV paths
3. Closes the resolver at the end (important — no resolver leaks)
importPlans() — read CSV from DAM → parse lines → PageManager.create() → Node.setProperty()
This method:
1. Builds path to CSV binary: csvPath + "/jcr:content/renditions/original/jcr:content"
2. Adapts the resource to InputStream to read the file
3. Uses PageManager.create() to create a CQ Page per plan
4. Uses Node.setProperty() (JCR API) to write planName, cost, validity, benefits, offers
5. Calls resolver.commit() to persist changes to JCR
6. Skips pages that already exist (checks with pageManager.getPage())
⏰ SimpleScheduledTask.java OSGi Scheduler (Demo)
@Component(service=Runnable.class) + @Designate
Same scheduler pattern as PlanCardScheduler but simpler. Runs every 30 seconds. Has a configurable myParameter that is logged on each execution. This is the archetype demo scheduler.
scheduler_expression = "*/30 * * * * ?" / scheduler_concurrent = false
scheduler_concurrent = false means if the previous run hasn't finished, the next scheduled run is skipped. This prevents overlapping executions — important for jobs that write to JCR.

Filter — LoggingFilter.java

🔍 LoggingFilter.java Sling Filter
@Component(service = Filter.class, property = { EngineConstants.SLING_FILTER_SCOPE + "=" + EngineConstants.FILTER_SCOPE_REQUEST })
Registers this as a Sling Servlet Filter. The property SLING_FILTER_SCOPE = REQUEST means this filter intercepts every incoming HTTP request to AEM before it reaches the servlet/component. Other scopes are: INCLUDE, FORWARD, ERROR, COMPONENT.
@ServiceRanking(-700)
Filters are executed in order of their service ranking. Lower negative numbers run later. -700 means this filter runs fairly late in the filter chain — after more critical filters. If you need a filter to run first, use a high positive number.
doFilter(request, response, filterChain)
The core filter method. It:
1. Casts ServletRequest to SlingHttpServletRequest to access Sling-specific methods
2. Logs the resource path and selector string at DEBUG level
3. Calls filterChain.doFilter(request, response) — this is MANDATORY. Without this line, the request never reaches the component/servlet.
init(FilterConfig) / destroy()
Lifecycle methods from the javax.servlet.Filter interface. Must be implemented even if empty. init() is called once when the filter is first loaded; destroy() when it's removed.

Listener — SimpleResourceListener.java

👂 SimpleResourceListener.java Resource Change Listener
@Component(service = ResourceChangeListener.class, immediate = true)
Registers as a ResourceChangeListener — an OSGi service that Sling calls whenever resources in the JCR change. immediate = true is required for event handlers and listeners to ensure they are active before any events fire.
public void onChange(List<ResourceChange> changes)
Called by Sling whenever a JCR change occurs. Each ResourceChange object has:
• getType() — ADDED, REMOVED, CHANGED, PROVIDER_ADDED, PROVIDER_REMOVED
• getPath() — the JCR path of the changed resource
• isExternal() — whether the change came from another cluster node
The listener simply logs each change at DEBUG level.

Servlet — SimpleServlet.java

🌐 SimpleServlet.java Sling Servlet
@SlingServletResourceTypes(resourceTypes="teleconnect/components/page", methods=HttpConstants.METHOD_GET, extensions="txt")
Binds this servlet to a resource type + method + extension combination. This servlet is invoked when a GET request is made to any resource of type teleconnect/components/page with the .txt extension. Example URL: /content/teleconnect/us/en/home.txt
extends SlingSafeMethodsServlet
SlingSafeMethodsServlet is for read-only (idempotent) HTTP methods (GET, HEAD). If you need POST/PUT/DELETE, extend SlingAllMethodsServlet instead. This is a key Sling interview point.
doGet() — resource.getValueMap().get(JcrConstants.JCR_TITLE)
Reads the jcr:title property from the requested resource's ValueMap and writes it to the response as plain text. Demonstrates the pattern: get resource from request → read from ValueMap → write to response.

HTL Templates (All Components)

📄 header.html HTL Template
data-sly-use.model="com.teleconnect.core.core.models.HeaderModel"
data-sly-use instantiates the Sling Model and binds it to the variable model. HTL automatically adapts the current request to this class. This is the bridge between Java backend and HTML template.
data-sly-test="${model.logoPath}" on <img>
data-sly-test is the HTL conditional. If logoPath is null or empty, the img element is not rendered at all. This prevents broken image tags on the page.
data-sly-list.navItem="${model.navLinks}"
data-sly-list iterates over the list returned by getNavLinks(). Each iteration exposes navItem (the current NavLink). It also provides navItem_list.index, navItem_list.count, navItem_list.first, navItem_list.last as loop status variables.
📄 planlist.html HTL Template
data-sly-use.model="com.teleconnect.core.core.models.PlanListModel"
Loads PlanListModel. The model's @PostConstruct init() has already run before HTL gets control, so model.plans is already populated with data from Content Fragments.
${itemList.index == 1 ? 'featured' : ''}
itemList is the loop status object in a data-sly-list. itemList.index is 0-based. So index 1 = second card = "Most Popular" featured card. This applies the CSS class conditionally.
data-sly-test="${!model.hasPlans}" class="plan-section__empty"
Shows an empty state message only when getHasPlans() returns false. This is defensive rendering — the page never shows a blank grid.
📄 schedulerplanlist.html HTL Template
id="splGrid_${model.instanceId}"
Uses the unique instanceId from the model (hash of component path) so JS can target this specific component when multiple instances of it are on the same page.
data-initial="${model.initialCount}" data-instance="${model.instanceId}"
Embeds model data as HTML data attributes. The JavaScript file (schedulerplanlist.js) reads these to know how many cards to show initially and which grid to target.
data-sly-test="${plan.addedAdvantage}" / data-sly-test="${plan.offers}"
Optional fields — only rendered if the plan has an addedAdvantage or offers value. This is proper conditional rendering in HTL.
📄 customheaderlibs.html / customfooterlibs.html ClientLib Inclusion
data-sly-use.clientlib="core/wcm/components/commons/v1/templates/clientlib.html"
Loads the AEM Core Components client library template — a reusable HTL template that provides clientlib.css and clientlib.js helper functions.
data-sly-call="${clientlib.css @ categories='teleconnect.base'}"
data-sly-call invokes the helper function, injecting all CSS from the clientlib category teleconnect.base. This renders the <link> tag pointing to the merged CSS file. Similarly for JS with clientlib.js.

End-to-End Data Flow

How plan data gets from a CSV file to the browser:

1

Author uploads CSV to DAM

CSV files (prepaid-plans.csv, postpaid-plans.csv, broadband-plans.csv) are uploaded to /content/dam/teleconnect/plans/ in AEM Assets.

2

PlanCardScheduler runs on cron

Every minute (0 * * * * ?), the scheduler reads each CSV via InputStream, parses rows, and uses PageManager.create() to create CQ Pages under /content/teleconnect/us/en/prepaid (and postpaid/broadband).

3

CQ Pages written to JCR

Each plan becomes a cq:Page. jcr:content has planName, cost, validity, benefits, offers as JCR properties. resolver.commit() saves to the repository.

4

Browser requests a page

User visits /content/teleconnect/us/en/home.html. LoggingFilter intercepts, logs the request path and selectors, then calls filterChain.doFilter() to pass it through.

5

Sling resolves component → HTL

AEM renders the schedulerplanlist component. HTL runs data-sly-use to instantiate SchedulerPlanListModel, adapting the request.

6

SchedulerPlanListModel.init() runs

@PostConstruct reads the configured plansRootPath, traverses child cq:Pages, reads plan data from each jcr:content ValueMap, builds List<PlanItem>.

7

HTL renders plan cards

data-sly-list iterates model.plans, emitting one .spl-card div per plan. data-initial and data-instance are written as HTML data attributes for JS.

8

ClientLibs load → JS enhances

customfooterlibs.html includes teleconnect.components JS. schedulerplanlist.js reads data-initial to hide extra cards, wires the "See More" button.

Likely Interview Questions & Answers

Q: What is a Sling Model? Why do we use it?
A Sling Model is a POJO annotated with @Model that gets injected with data from the current request or resource. We use it to separate Java logic from the HTL template. In our project, all components like HeaderModel, PlanListModel have Sling Models. Instead of writing Java inside the template, the model prepares all data and the template just renders it.
Q: What is the difference between adaptables = Resource.class and SlingHttpServletRequest.class?
Resource.class: model gets the current resource only — simpler, no request context. Used in HeroBannerModel.
SlingHttpServletRequest.class: model gets the full request including session, parameters, and the resource. Used when you need @SlingObject ResourceResolver (like PlanListModel, HeaderModel).
Q: What is @PostConstruct and when is it called?
@PostConstruct marks a method that Sling Models call automatically after all field injections (@ValueMapValue, @ChildResource, etc.) are complete. It is the initialization step. We use it in PlanListModel to fetch Content Fragments and build the plans list, and in HelloWorldModel to build the message string.
Q: How does PlanListModel read Content Fragments?
It uses ResourceResolver.getResource(cfRootPath) to get the DAM folder, then iterates children. Each child is adapted using child.adaptTo(ContentFragment.class). Then cf.getElement("planName").getValue().getValue() reads each field. The CF folder path is determined by the authored productType value (prepaid/postpaid/broadband).
Q: Explain how the Scheduler works in this project.
PlanCardScheduler implements Runnable and is annotated @Component(service=Runnable.class). In @Activate, it registers itself with the Sling Scheduler service using a cron expression. Every minute, run() is called — it opens a ResourceResolver, reads 3 CSV files from DAM, parses them, and creates CQ Pages per plan using PageManager.create() and Node.setProperty(). @Deactivate unregisters the job to prevent memory leaks.
Q: What is a Sling Filter? How is LoggingFilter registered?
A Sling Filter implements javax.servlet.Filter and intercepts requests before they reach the component. LoggingFilter is registered with SLING_FILTER_SCOPE=REQUEST so it runs on every HTTP request. The @ServiceRanking(-700) determines when in the filter chain it runs. It MUST call filterChain.doFilter(), otherwise the request is blocked.
Q: What is @ChildResource and when do you use it?
@ChildResource injects child nodes of the current resource as a List of inner Sling Models. We use it in HeaderModel for navLinks and FooterModel for footerLinks — these are multifield dialog values stored as child nodes in JCR. Each child node maps to the inner NavLink/FooterLink Sling Model (adaptable from Resource.class).
Q: What HTL directives did you use and what do they do?
data-sly-use: loads a Sling Model or Java class
data-sly-list: iterates a collection
data-sly-test: conditional rendering (renders element only if true)
data-sly-call: calls a function from a loaded template
data-sly-resource: includes another resource
${properties.*}: reads JCR properties directly without a model
${model.*}: accesses model getter methods
Q: Why is resolver.close() important in the scheduler?
ResourceResolvers are connections to the JCR repository. If not closed, they stay open and cause resource/memory leaks. In PlanCardScheduler.run(), we call resolver.close() in a finally-like manner after all operations. Also, resolver.commit() must be called explicitly to persist JCR changes — without it, all writes are lost when the resolver is closed.
Q: What is the difference between PlanListModel and SchedulerPlanListModel?
PlanListModel reads plan data from Content Fragments in DAM — structured data authored by content editors using CF models.
SchedulerPlanListModel reads plan data from CQ Pages created by the PlanCardScheduler — pages generated automatically from CSV files uploaded to DAM. Same output (list of plan cards), but completely different data sources.
